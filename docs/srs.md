# Software Requirements Specification

Специфікація вимог до програмного забезпечення мультиагентної системи декомпозиції та
планування задач програмних проєктів. Структура документа відповідає ISO/IEC/IEEE 29148:2018.

## 1. System Context

### 1.1. Призначення та межі системи (Scope)

Система приймає вхідний артефакт вимог (епік або технічне завдання), формує ієрархічний план
задач з оцінками трудомісткості та графом залежностей і після підтвердження користувачем
синхронізує план з GitHub Issues.

До меж системи належать: прийом та валідація вхідних файлів, оркестрування агентів, збереження
стану сеансів, синхронізація з трекером, трасування та облік вартості викликів LLM.

Поза межами системи: керування спринтами, облік фактично витраченого часу, двостороння
синхронізація змін, внесених безпосередньо в GitHub.

### 1.2. Актори та зовнішні системи

| Тип | Назва | Взаємодія |
| --- | --- | --- |
| Актор | Project Owner | Підключає репозиторій GitHub, керує ролями учасників проєкту, затверджує план |
| Актор | Planner | Завантажує епіки, переглядає та редагує згенерований план, затверджує план |
| Актор | Viewer | Переглядає сеанси та плани без права змін |
| Зовнішня система | Claude API (Anthropic) | Генерація структурованих відповідей агентів, HTTPS/REST |
| Зовнішня система | GitHub | OAuth 2.0 автентифікація, REST API v3 для Issues, Labels, Milestones |

### 1.3. Обмеження

- Розгортання виконується в середовищі Docker Compose на одному хості.
- Мова вхідних артефактів: українська або англійська.
- Підтримувані формати вхідних файлів: Markdown (`.md`), PDF з текстовим шаром.

## 2. Functional Requirements

### 2.1. Автентифікація та авторизація

#### SRS-FUN-01

Система повинна автентифікувати користувача через GitHub OAuth 2.0 (Authorization Code Flow з PKCE).

#### SRS-FUN-02

Система повинна видавати після успішної автентифікації пару токенів: access JWT та refresh-токен.

#### SRS-FUN-03

Система повинна перевіряти роль користувача (Owner, Planner, Viewer) та належність ресурсу до
проєкту користувача для кожного запиту до сеансів і планів.

### 2.2. Сеанси планування

#### SRS-FUN-04

Система повинна приймати файл епіку у форматі Markdown або PDF розміром до 10 МБ та відхиляти
файли інших форматів із кодом HTTP 415.

#### SRS-FUN-05

Система повинна створювати сеанс планування зі статусом `QUEUED` та публікувати подію
`session.created` у брокер повідомлень.

#### SRS-FUN-06

Система повинна транслювати зміни статусу сеансу клієнту через Server-Sent Events.

### 2.3. Агентне оркестрування

#### SRS-FUN-07

Система повинна декомпозувати вхідний артефакт на ієрархію Epic → Story → Task, валідовану за
JSON Schema.

#### SRS-FUN-08

Система повинна призначати кожній задачі оцінку в story points зі шкали Фібоначчі
(1, 2, 3, 5, 8, 13) з урахуванням k = 5 семантично найближчих завершених задач.

#### SRS-FUN-09

Система повинна будувати орієнтований граф залежностей між задачами, виявляти цикли та
обчислювати критичний шлях.

#### SRS-FUN-10

Система повинна повертати план на доопрацювання за результатами верифікації не більше 3 разів
на сеанс.

#### SRS-FUN-11

Система повинна призупиняти сеанс у статусі `AWAITING_APPROVAL` до явного рішення користувача
(затвердити або відхилити план).

#### SRS-FUN-12

Система повинна відновлювати виконання сеансу з останнього збереженого стану (checkpoint) після
перезапуску Agent Orchestrator.

### 2.4. Синхронізація з GitHub Issues

#### SRS-FUN-13

Система повинна створювати для затвердженого плану issues, labels та milestones у вибраному
репозиторії GitHub через інструменти GitHub MCP Server.

#### SRS-FUN-14

Система повинна присвоювати кожній задачі плану ключ синхронізації та не створювати повторно
issue, для якого ключ уже зареєстровано.

### 2.5. Спостережуваність та контроль вартості

#### SRS-FUN-15

Система повинна реєструвати для кожного виклику LLM кількість вхідних і вихідних токенів,
тривалість та вартість.

#### SRS-FUN-16

Система повинна завершувати сеанс зі статусом `BUDGET_EXCEEDED`, якщо сумарна кількість токенів
сеансу перевищує ліміт [SRS-NFR-COST-01](#srs-nfr-cost-01).

#### SRS-FUN-17

Система повинна записувати в журнал аудиту події: вхід користувача, створення сеансу,
затвердження плану, синхронізацію з GitHub, зміну ролі.

## 3. Non-Functional Requirements

### 3.1. Продуктивність та масштабованість

#### SRS-NFR-PERF-01

Час відгуку синхронних REST-ендпоінтів (без виклику LLM) повинен становити p95 ≤ 200 мс при
навантаженні 200 RPS.

#### SRS-NFR-PERF-02

Час створення сеансу (прийом файлу до 10 МБ та публікація події) повинен становити p95 ≤ 500 мс.

#### SRS-NFR-PERF-03

Тривалість повного сеансу планування для епіку до 20 сторінок і до 60 задач повинна становити
p95 ≤ 180 с.

#### SRS-NFR-PERF-04

Затримка доставки події прогресу через SSE повинна становити ≤ 1 с від завершення вузла графа.

#### SRS-NFR-SCAL-01

Система повинна обробляти не менше 20 паралельних сеансів планування; масштабування виконується
збільшенням кількості реплік Agent Orchestrator (competing consumers) без зміни коду.

### 3.2. Вартість (FinOps)

#### SRS-NFR-COST-01

Сумарна кількість токенів одного сеансу не повинна перевищувати 250 000 (input + output).

#### SRS-NFR-COST-02

Відповідь LLM для одного виклику агента повинна обмежуватися параметром `max_tokens` ≤ 8 192.

### 3.3. Безпека та комплаєнс

#### SRS-NFR-SEC-01

Access JWT повинен підписуватися алгоритмом RS256 і мати TTL 15 хв; refresh-токен — TTL 7 діб,
зберігання в cookie з атрибутами `HttpOnly`, `Secure`, `SameSite=Strict`.

#### SRS-NFR-SEC-02

Токени доступу GitHub повинні зберігатися в БД у зашифрованому вигляді (AES-256-GCM); ключ
шифрування передається через змінну середовища і не зберігається в репозиторії.

#### SRS-NFR-SEC-03

Кількість запитів повинна обмежуватися алгоритмом Token Bucket: 60 запитів/хв на користувача та
10 нових сеансів/год; у разі перевищення — HTTP 429 із заголовком `Retry-After`.

#### SRS-NFR-SEC-04

Вміст вхідних документів повинен передаватися в LLM лише як дані в окремому блоці, ізольованому
від системних інструкцій; агентам доступні лише інструменти MCP з білого списку
(`create_issue`, `create_label`, `create_milestone`, `list_issues`).

#### SRS-NFR-SEC-05

Зовнішні з'єднання повинні використовувати TLS 1.2+; заголовки безпеки HTTP (HSTS, CSP,
X-Content-Type-Options) повинні бути встановлені на рівні Reverse Proxy.

#### SRS-NFR-SEC-06

Система повинна відповідати OWASP ASVS 4.0 Level 2 та враховувати OWASP Top 10 for LLM
Applications (LLM01 Prompt Injection, LLM06 Excessive Agency).

#### SRS-NFR-SEC-07

Docker-образи та залежності не повинні містити вразливостей рівня CRITICAL або HIGH на момент
релізу.

#### SRS-NFR-SEC-08

Система повинна видаляти завантажені файли та дані сеансів користувача протягом 24 год після
запиту на видалення облікового запису (GDPR, стаття 17).

### 3.4. Надійність

#### SRS-NFR-REL-01

Доступність API Service повинна становити не менше 99.5 % на календарний місяць.

#### SRS-NFR-REL-02

Виклики Claude API та GitHub API повинні повторюватися до 3 разів з експоненційною затримкою
1 → 2 → 4 с та jitter; Circuit Breaker повинен переходити у стан Open після 5 послідовних помилок
і в стан Half-Open через 30 с.

#### SRS-NFR-REL-03

Втрата виконаної роботи сеансу внаслідок збою worker-а не повинна перевищувати один вузол графа.

#### SRS-NFR-REL-04

Повторна доставка події синхронізації не повинна створювати дублікатів issues; повідомлення,
не оброблене після 5 спроб, повинно переміщуватися в Dead Letter Queue.

#### SRS-NFR-REL-05

Резервне копіювання PostgreSQL повинно виконуватися щоденно; RPO ≤ 24 год, RTO ≤ 1 год.

### 3.5. Інфраструктура та якість коду

#### SRS-NFR-INF-01

Кожен сервіс повинен постачатися як Docker-образ із healthcheck та підтримувати graceful
shutdown тривалістю ≤ 30 с.

#### SRS-NFR-QA-01

Покриття коду backend автоматизованими тестами повинно становити ≥ 70 %; SonarQube Quality Gate
повинен не містити Blocker та Critical issues; mypy у режимі `strict` — без помилок.

#### SRS-NFR-OBS-01

100 % викликів LLM та MCP-інструментів повинні містити `trace_id`; сервіси повинні експортувати
метрики RED (Rate, Errors, Duration) у Prometheus.

## 5. Glossary

| Термін | Визначення |
| --- | --- |
| Agent | Компонент, що виконує одну роль у графі (Planner, Estimator, Dependency Analyzer, Reviewer) шляхом виклику LLM та детермінованого коду |
| Checkpoint | Збережений у PostgreSQL знімок стану графа агентів після виконання вузла; використовується для відновлення сеансу |
| Circuit Breaker | Патерн відмовостійкості, що тимчасово блокує виклики до зовнішнього сервісу після серії помилок |
| Human-in-the-Loop (HITL) | Режим, у якому граф агентів призупиняється до рішення користувача (LangGraph interrupt) |
| JWT | JSON Web Token (RFC 7519) — підписаний токен доступу з набором claims |
| MCP | Model Context Protocol — відкритий протокол надання LLM-застосункам інструментів і даних через стандартизований клієнт-серверний інтерфейс |
| RAG | Retrieval-Augmented Generation — доповнення запиту до LLM даними, отриманими пошуком (тут — векторний пошук у pgvector) |
| Story point | Відносна одиниця оцінки трудомісткості задачі за шкалою Фібоначчі |
| Transactional Outbox | Патерн, за яким подія записується в таблицю outbox у тій самій транзакції, що й зміна даних, і публікується окремим процесом |
| p95 | 95-й перцентиль: значення, яке не перевищують 95 % вимірювань |
