# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.1. Актуальність вибраної теми дослідження

Декомпозиція вимог великих програмних проєктів на атомарні задачі з оцінками трудомісткості та
залежностями визначає точність планування релізів і розподілу ресурсів команди. У поточній
практиці ця операція виконується технічним лідером вручну в трекері задач: витрати часу
зростають пропорційно обсягу вимог, оцінки залежать від досвіду виконавця, а неявні залежності
між задачами виявляються лише на етапі реалізації. Наявні засоби генеративного ШІ в трекерах
задач працюють у режимі одиночного запиту до великої мовної моделі (LLM) і не забезпечують
верифікації результату, збереження стану тривалої операції та ідемпотентного запису у зовнішню
систему.

Інженерна складність задачі полягає в поєднанні недетермінованої поведінки LLM з вимогами до
відмовостійкості та продуктивності: сеанс планування містить від 6 до 15 послідовних викликів
LLM тривалістю до 180 с, тоді як синхронні інтерфейси системи повинні відповідати за
p95 ≤ 200 мс. Для коректної роботи необхідні асинхронна обробка з відновленням після збоїв,
обмеження вартості обчислень за кількістю токенів, захист від prompt injection у вхідних
документах та гарантія відсутності дублікатів під час синхронізації з трекером. Поява
стандартизованого протоколу Model Context Protocol (MCP), який підтримують провідні трекери
задач, створює технологічну основу для такої інтеграції.

## 1.2. Огляд сучасних підходів до вирішення відповідних завдань

Підходи до автоматизації декомпозиції та планування задач програмних проєктів можна
класифікувати за способом формування плану та механізмом його перевірки.

**Ручна декомпозиція за структурою робіт (WBS) з експертним оцінюванням.** План формується
технічним лідером; оцінки визначаються методами Planning Poker або Wideband Delphi. Підхід
забезпечує врахування контексту команди, але має лінійну залежність витрат часу від обсягу
вимог і не гарантує відтворюваності оцінок між виконавцями.

**Шаблонна автоматизація трекерів.** Правила автоматизації (Jira Automation, GitHub Actions)
створюють типові набори задач за шаблоном при настанні події. Підхід детермінований і дешевий,
але не аналізує зміст вимог і не застосовний до нетипових епіків.

**Одиночний запит до LLM.** Модель генерує перелік задач за текстом вимог за один виклик
(функції ШІ-асистентів у трекерах). Підхід усуває ручну працю на етапі чернетки, але не містить
перевірки повноти, циклічних залежностей і узгодженості оцінок; результат обмежено контекстним
вікном моделі та не відтворюється між запусками.

**Агентні підходи.** Схема ReAct (поєднання міркувань і викликів інструментів) та мультиагентні
системи розподіляють задачу між спеціалізованими агентами з циклом самоперевірки. Фреймворки
класу LangGraph подають такий процес як граф станів зі збереженням проміжних результатів і
точками призупинення для рішення людини (human-in-the-loop). Доповнення генерації пошуком
(Retrieval-Augmented Generation) дає змогу калібрувати оцінки за історичними даними проєкту.
Основні інженерні ризики підходу — необмежені цикли агентів, неконтрольована вартість викликів
і надмірні повноваження агентів щодо зовнішніх систем (OWASP Top 10 for LLM Applications,
LLM06).

**Стандартизація доступу агентів до інструментів.** Model Context Protocol визначає
клієнт-серверний інтерфейс, через який LLM-застосунок отримує інструменти та дані зовнішніх
систем. Протокол замінює спеціалізовані інтеграції для кожного трекера уніфікованим набором
інструментів і дає змогу обмежити доступ агента білим списком операцій.

Для поставленої задачі обрано агентний підхід з графом станів, детермінованою перевіркою
графа залежностей, RAG-калібруванням оцінок і доступом до трекера через MCP. Детерміновані
перевірки та контроль вартості компенсують основні ризики агентних систем.

## 1.3. Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів

### 1.3.1. Методика відбору та аналізу

Для аналізу обрано три системи керування задачами, що містять функцію декомпозиції задач
засобами генеративного ШІ та програмний інтерфейс для автоматизованого створення задач:

1. Jira Cloud з агентами Atlassian Rovo.
2. Linear з інтеграцією агентів через Model Context Protocol.
3. ClickUp з модулем ClickUp Brain.

Системи розглянуто як інженерні об'єкти за чотирма аспектами: архітектурний патерн, протоколи
взаємодії, стек даних і механізми консистентності, технічні обмеження (bottlenecks). Дані
отримано з офіційної документації та технічних публікацій розробників; внутрішня реалізація
закритих компонентів, не описана публічно, у висновках не використовується. Перелік джерел
наведено в кінці підрозділу.

### 1.3.2. Jira Cloud та Atlassian Rovo

**Архітектурний патерн.** Початкова хмарна версія Jira використовувала кодову базу серверного
продукту з додатковими хмарними шарами, у якій бізнес-логіка була тісно пов'язана зі схемою БД.
Платформа поступово переводиться на мультиорендну архітектуру з окремими сервісами, зокрема
сервісом зберігання задач Jira Issue Store, розрахованим на масштаб до 1 млрд задач на
орендаря. Агенти Rovo працюють поверх платформи як окремі виконавці, яких можна призначити на
задачу; запуск агентів виконується правилами Jira Automation, а дії — у межах прав доступу
користувача.

**Протоколи взаємодії.** REST API v3 та GraphQL API платформи Atlassian для інтеграцій;
вебхуки для подій; віддалений MCP-сервер Atlassian для доступу LLM-агентів до задач (пошук за
JQL, створення підзадач, зміна статусів).

**Стек даних і консистентність.** Дані кожного орендаря зберігаються в окремій БД PostgreSQL:
близько 4 млн баз даних на ~3000 серверах у 13 регіонах AWS, з міграцією з Amazon RDS на
Aurora PostgreSQL. Модель «БД на орендаря» забезпечує ізоляцію даних і транзакційну
консистентність ACID у межах орендаря, але ускладнює операції обслуговування та міграції схеми
в масштабі флоту.

**Технічні обмеження.**

- З березня 2026 року для застосунків діють три незалежні механізми обмеження запитів:
  погодинна квота в балах (вартість запиту залежить від кількості задіяних об'єктів),
  посекундне обмеження пікових запитів і обмеження частоти запису в одну задачу. Пакетне
  створення плану з десятків задач із залежностями споживає квоту нелінійно та завершується
  відповідями HTTP 429, що потребує керування повторними запитами на боці інтеграції.
- Декомпозиція епіку агентом Rovo виконується як генерація чернетки задач з подальшим
  підтвердженням користувачем. Публічна документація не описує детермінованої перевірки
  графа залежностей, обчислення критичного шляху або калібрування оцінок за історичними
  даними.
- Тісний зв'язок бізнес-логіки зі схемою БД у спадковому коді Atlassian визначає як основне
  обмеження горизонтального масштабування, що зумовило багаторічну реархітектуру.

### 1.3.3. Linear

**Архітектурний патерн.** Linear побудовано за принципом local-first із власним рушієм
синхронізації (sync engine). Клієнт підтримує граф об'єктів у пам'яті та зберігає його в
IndexedDB, що дозволяє виконувати зміни без очікування відповіді сервера. Сервер синхронізації
відстежує журнал реплікації PostgreSQL і передає клієнтам дельти змін.

**Протоколи взаємодії.** GraphQL API для запитів і мутацій; WebSocket для доставки змін у
реальному часі; вебхуки; офіційний віддалений MCP-сервер (`mcp.linear.app`), через який
LLM-агенти отримують інструменти роботи з задачами, проєктами, циклами та коментарями,
зокрема інструменти зміни даних.

**Стек даних і консистентність.** PostgreSQL як основне сховище; клієнтські зміни застосовуються
оптимістично і підтверджуються сервером, тобто клієнтські копії перебувають у стані eventual
consistency відносно сервера.

**Технічні обмеження.**

- Модель local-first передбачає завантаження значної частини даних робочого простору на
  клієнт; розробники Linear окремо публікували матеріали про масштабування рушія синхронізації
  та перебудову шляху читання дельт, що вказує на зростання вартості початкового завантаження
  і синхронізації зі збільшенням обсягу даних.
- Функції декомпозиції задач реалізуються зовнішніми агентами через MCP-сервер. Агент
  отримує повний набір інструментів, включно з інструментами запису, тому контроль надмірних
  повноважень (OWASP LLM06 Excessive Agency) і підтвердження змін людиною залежать від
  реалізації конкретного агента, а не від платформи.
- Перевірка коректності згенерованого плану (цикли залежностей, повнота покриття вимог) та
  облік вартості LLM-викликів не є частиною платформи.

### 1.3.4. ClickUp та ClickUp Brain

**Архітектурний патерн.** ClickUp — багатофункціональна SaaS-платформа керування задачами з
вбудованим модулем ШІ ClickUp Brain. За даними сторонніх оглядів, Brain надає доступ до кількох
LLM (зокрема моделей OpenAI та Anthropic) через єдиний інтерфейс; за заявою розробника, дані
клієнтів не використовуються для навчання моделей. Публічна документація щодо внутрішньої
архітектури сервісів відсутня.

**Протоколи взаємодії.** REST API v2 з авторизацією за персональним токеном або OAuth 2.0;
вебхуки для подій.

**Стек даних і консистентність.** Тип СУБД і механізми консистентності публічно не описані.

**Технічні обмеження.**

- Обмеження API: 100 запитів/хв на токен для тарифів Free Forever, Unlimited і Business;
  1 000 — для Business Plus; 10 000 — для Enterprise; перевищення — HTTP 429. На базових
  тарифах синхронізація плану з 60 задач з мітками, залежностями та призначеннями (3–4 запити
  на задачу) займає 2–3 хв без урахування повторів.
- Функція «Suggest subtasks» формує підзадачі одного рівня на основі опису та коментарів однієї
  задачі. Контекст генерації обмежено цією задачею; побудова ієрархії Epic → Story → Task,
  графа залежностей і оцінок трудомісткості не передбачена.
- Відсутність публічної інженерної документації унеможливлює верифікацію механізмів
  відмовостійкості та обробки помилок LLM.

### 1.3.6. Аналітичний висновок підрозділу

Аналіз показав, що в усіх трьох системах генерація плану задач реалізована як одноетапна
операція LLM із ручним підтвердженням результату. Перевірка графа залежностей, обчислення
критичного шляху й калібрування оцінок за історичними даними у публічній документації не
описані. У Linear і в MCP-інтеграціях Jira агент отримує інструменти запису безпосередньо, тому
відповідальність за обмеження повноважень і запобігання дублюванню задач перекладається на
реалізацію інтеграції. Обмеження API аналогів (квоти в балах у Jira, 100 запитів/хв у ClickUp)
роблять пакетне створення плану чутливим до відповідей HTTP 429, а документованих механізмів
ідемпотентного повторення в цих сценаріях немає.

Із рішень аналогів у роботі використано два. Перше — стандартизований доступ LLM-агентів до
трекера задач через Model Context Protocol, який підтримують і Atlassian, і Linear. Друге —
ізоляція даних за межами відповідальності (у системі — на рівні проєкту з перевіркою
належності ресурсу для кожного запиту). Від аналогів система відрізняється трьома інженерними
механізмами. Генерація плану виконується графом агентів зі збереженням стану після кожного
кроку та обмеженням циклу верифікації. Залежності аналізуються детермінованим алгоритмом без
участі LLM. Запис у трекер виконує окремий сервіс з ключем ідемпотентності, Transactional
Outbox та експоненційною затримкою з урахуванням `Retry-After`, а агенти LLM не мають прав на
запис.

Отже, компроміс обраного рішення полягає в більшій інфраструктурній складності (брокер
повідомлень, окремі сервіси синхронізації та MCP) в обмін на відтворюваність результату,
контрольовану вартість і цілісність даних у зовнішній системі. Архітектурну реалізацію цих
механізмів розглянуто в Розділі 2.

## 1.4. Аналіз обраної предметної області в межах дослідження (модель As-Is)

### 1.4.1. Загальна характеристика домену

Предметною областю є планування робіт у командній розробці програмного забезпечення: перетворення
вимог (епіків, технічних завдань) на впорядкований набір задач у трекері задач з оцінками
трудомісткості, залежностями та розподілом за ітераціями. Процес повторюється для кожного
епіку протягом усього життєвого циклу продукту і впливає на точність планування релізів.

Станом на 2026 рік у домені спостерігаються три тенденції: вбудовування функцій генеративного
ШІ в трекери задач (Atlassian Rovo, ClickUp Brain); поява агентних інтеграцій через Model
Context Protocol, які надають LLM-агентам доступ до задач трекера; посилення обмежень швидкості
API трекерів (система лімітів у балах у Jira Cloud з березня 2026 року), що ускладнює пакетні
операції інтеграцій.

### 1.4.3. Бізнес-процеси As-Is та вузькі місця

**Процес 1. Ручна декомпозиція епіку.**

1. Технічний лідер читає епік і формує ієрархію задач у текстовому редакторі або безпосередньо
   в трекері.
2. Оцінки визначаються на зустрічі команди (Planning Poker), як правило 1–2 год на епік.
3. Задачі вводяться в трекер вручну або послідовними запитами REST API за власним скриптом.
4. Залежності між задачами фіксуються текстовими посиланнями в описі або не фіксуються.

Вузькі місця: витрати часу технічного лідера лінійно залежать від обсягу вимог; залежності не
формалізовані як граф, тому цикли та критичний шлях не виявляються до початку реалізації;
оцінки не зіставляються з історичними даними проєкту.

**Процес 2. Генерація плану одиночним запитом до LLM.**

1. Користувач передає текст епіку ШІ-асистенту трекера або в чат LLM.
2. Модель повертає перелік задач у вільному форматі; користувач переносить або підтверджує їх.
3. За збою з'єднання чи тайм-ауту (тривалість відповіді для великого епіку — десятки секунд)
   запит виконується повторно з нуля.

Вузькі місця: результат не валідується за схемою і не перевіряється на повноту покриття вимог;
стан операції не зберігається, тому збій призводить до повторної оплати всіх токенів; вміст
епіку змішується з інструкціями моделі, що створює вектор prompt injection; вартість викликів
не обліковується.

**Процес 3. Пакетне створення задач у трекері.**

1. Скрипт інтеграції послідовно викликає API трекера для кожної задачі, мітки й віхи.
2. На відповідь HTTP 429 або 5xx скрипт завершується з помилкою або повторює запит без
   урахування заголовка `Retry-After`.
3. Повторний запуск скрипта створює задачі заново.

Вузькі місця: відсутність ідемпотентності призводить до дублікатів задач при повторному
запуску; синхронний скрипт утримує з'єднання на весь час створення плану (2–3 хв для 60 задач
при ліміті 100 запитів/хв); стан частково виконаної синхронізації не фіксується.

### 1.4.4. Регуляторні та індустріальні обмеження

- **GDPR (Regulation (EU) 2016/679).** Епіки можуть містити персональні дані; необхідні
  мінімізація даних, право на видалення (стаття 17) та договірні гарантії провайдера LLM щодо
  невикористання даних для навчання.
- **OWASP Top 10 for LLM Applications.** Обов'язкові заходи проти prompt injection (LLM01),
  неналежної обробки виводу (LLM05) та надмірних повноважень агентів (LLM06).
- **OWASP ASVS 4.0 та OWASP API Security Top 10 (2023).** Вимоги до автентифікації, контролю
  доступу на рівні об'єктів і обмеження швидкості запитів.
- **Специфікація Model Context Protocol.** Визначає транспорт (Streamable HTTP), формат
  оголошення інструментів і модель авторизації, з якими має бути сумісна інтеграція.
- **Обмеження API трекерів.** Документовані ліміти запитів і відповіді HTTP 429 з
  `Retry-After` є зовнішнім обмеженням, яке система зобов'язана враховувати під час
  синхронізації.
- **ISO/IEC/IEEE 29148:2018.** Стандарт специфікації вимог, застосований до формалізації
  вимог системи.

Виявлені вузькі місця визначають мету автоматизації: формування плану з перевіркою графа
залежностей, відновлення операції після збоїв без повторних витрат, контроль вартості LLM та
ідемпотентна синхронізація з трекером з урахуванням його обмежень швидкості.

## 1.5. Постановка задачі та формування вимог

### 1.5.1. Концептуальна модель To-Be

У цільовому стані декомпозиція вимог виконується асинхронним конвеєром агентів зі збереженням
стану, а запис у трекер — окремим сервісом через MCP з контролем ідемпотентності:

1. Користувач завантажує епік через вебінтерфейс. Сервіс API валідує файл, створює сеанс зі
   статусом `QUEUED` і публікує подію в RabbitMQ; відповідь клієнту — HTTP 202 без очікування
   LLM.
2. Оркестратор агентів споживає подію та виконує граф Planner → Estimator → Dependency Analyzer
   → Reviewer. Після кожного вузла стан зберігається в PostgreSQL (checkpoint), тому збій
   процесу або LLM API не призводить до втрати виконаної роботи.
3. Прогрес сеансу транслюється у вебінтерфейс через Redis Pub/Sub і Server-Sent Events.
4. Reviewer повертає план на доопрацювання не більше 3 разів; далі граф переходить у стан
   `AWAITING_APPROVAL`.
5. Користувач редагує та затверджує план. Операції синхронізації записуються в таблицю outbox
   у тій самій транзакції, що й зміна статусу плану.
6. Сервіс синхронізації викликає інструменти GitHub MCP Server; кожна задача має ключ
   синхронізації, тому повторна обробка події не створює дублікатів.
7. Усі виклики LLM і MCP трасуються з обліком токенів і вартості сеансу.

Таблиця 1.4 — Відповідність вузьких місць As-Is рішенням To-Be

| Вузьке місце As-Is | Рішення To-Be |
| --- | --- |
| Ручна декомпозиція та оцінювання | Агенти Planner і Estimator з RAG за історичними задачами |
| Неформалізовані залежності | Детермінований аналіз графа: цикли, топологічне сортування, критичний шлях |
| Втрата стану при збоях LLM API | Checkpointing графа, Retry with Exponential Backoff, Circuit Breaker |
| Дублювання задач при синхронізації | Transactional Outbox і ключ ідемпотентності |
| Неконтрольована вартість LLM | Бюджет токенів на сеанс, ліміт ітерацій верифікації |
| Prompt injection через вміст епіку | Ізоляція вмісту документа від інструкцій; агенти без прав запису |

### 1.5.2. Функціональні вимоги (Core Features)

#### Модуль автентифікації та авторизації (API Service)

- Автентифікувати користувача через GitHub OAuth 2.0 і видавати пару JWT (access, refresh);
  зберігати токен GitHub у зашифрованому вигляді.
- Перевіряти роль користувача в проєкті (Owner, Planner, Viewer) і належність ресурсу проєкту
  для кожного запиту.

#### Модуль сеансів планування (API Service)

- Приймати файл епіку (Markdown, PDF ≤ 10 МБ), вилучати текст і створювати сеанс зі статусом
  `QUEUED` з публікацією події в брокер повідомлень.
- Транслювати зміни статусу сеансу та проміжні результати агентів через Server-Sent Events.

#### Модуль агентного оркестрування (Agent Orchestrator)

- Декомпозувати епік на ієрархію Epic → Story → Task зі структурованим виводом, валідованим
  за JSON Schema.
- Обчислювати story points з урахуванням k = 5 семантично найближчих завершених задач.
- Будувати граф залежностей, виявляти цикли та обчислювати критичний шлях.
- Верифікувати план і повертати його на доопрацювання не більше 3 разів.
- Призупиняти виконання до рішення користувача та відновлювати його з checkpoint.

#### Модуль синхронізації (Sync Worker, GitHub MCP Server)

- Створювати issues, labels і milestones у репозиторії GitHub через MCP з гарантією
  відсутності дублікатів.

#### Модуль спостережуваності

- Реєструвати кількість токенів, затримку та вартість кожного виклику LLM; завершувати сеанс
  зі статусом `BUDGET_EXCEEDED` при перевищенні бюджету.

### 1.5.4. Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка розподіленої
подієво-орієнтованої мультиагентної системи на основі графа станів LangGraph для вирішення

синхронних інтерфейсів p95 ≤ 200 мс при навантаженні 200 RPS.

## Висновки до розділу 1

Аналіз предметної області та існуючих рішень показав, що декомпозиція вимог у командній
розробці залишається переважно ручною операцією з лінійними витратами часу та
неформалізованими залежностями між задачами. Вбудовані ШІ-функції трекерів Jira Cloud,
Linear і ClickUp зводять генерацію плану до одноетапного запиту LLM: у їхній публічній
документації не описано перевірки графа залежностей, відновлення операції після збоїв і
обліку вартості викликів, а пакетне створення задач обмежене лімітами API без документованих
механізмів ідемпотентного повторення.

Обґрунтовано агентний підхід з графом станів як основу рішення. Поєднання спеціалізованих
агентів з детермінованим аналізом залежностей, RAG-калібруванням оцінок і збереженням стану
після кожного кроку усуває вузькі місця моделі As-Is, а подієво-орієнтований контур на основі
RabbitMQ і Transactional Outbox відокремлює тривалі сеанси від синхронних інтерфейсів.
Доступ до трекера через Model Context Protocol з білим списком інструментів і передачею
операцій запису окремому сервісу обмежує повноваження LLM-агентів відповідно до OWASP Top 10
for LLM Applications.

Сформульовано 11 функціональних і 20 вимірюваних нефункціональних вимог, що визначають
межі системи: p95 ≤ 200 мс для синхронних інтерфейсів, ≤ 180 с на сеанс планування, бюджет
250 000 токенів, відновлення з втратою не більше одного вузла графа та відсутність дублікатів
під час синхронізації. Формалізація цих вимог у специфікації ISO/IEC/IEEE 29148, проєктування
архітектури, моделі даних, API-контрактів і алгоритмів критичних вузлів є предметом Розділу 2,
а програмна реалізація, тестування та інструментальний аудит — Розділу 3.
